# AI Development Rules

## 开工前

1. 必须读取 `AGENTS.md`、`.ai/README.md` 和本目录关键 context。
2. 必须读取 `.ai/requirements/CURRENT_REQUIREMENT.md`。
3. 必须确认需求类型、目标、非目标、影响范围、验收标准、测试要求。
4. 必须检查当前 `git status`，识别用户已有改动。

## 编码中

1. 严禁修改当前需求范围之外的代码；开始编码前必须明确影响范围，发现无关问题只记录，不顺手修复、重构或格式化。
2. 所有接口驱动的后续流程，必须以接口明确返回成功为唯一触发条件：发起请求后必须等待响应并判定真实成败，仅成功后才可执行 callback、进入下一步、关闭弹层、展示成功提示、刷新数据、提交成功态或跳转；接口失败或抛出异常时必须进入失败分支并保留可重试状态，不得继续任何成功链路。该规则适用于读写接口和所有交互形态，不局限于弹层。
3. 不恢复、不覆盖用户已有未说明改动。
4. 不随意修改业务逻辑以满足测试。
5. 新增 API 走现有 request 封装。
6. 新增共享逻辑优先放 `packages/*`，但必须保持业务无关。
7. 新增 app 内逻辑优先放当前 domain，不要过早抽象。
8. UI 修改按所属 app 样式系统执行。
9. 新增或接入 qiankun 微应用时必须启用样式隔离；微应用样式不得污染宿主全局 `html` / `body`，业务背景应写到微应用 root 容器或局部作用域。
10. ABI 页面路由由应用启动时的 Elegant Router 插件根据 `apps/abi/src/pages` 目录与页面 `config.ts` 自动生成；开发时只维护页面目录和配置，不手工执行路由生成命令，也不手工编辑 `src/router/elegant/*` 或 `src/types/elegant-router.d.ts` 生成文件，除非用户明确要求。

## 测试与验证

1. 测试只需要覆盖和执行当前修改内容对应的定向测试；除非用户明确要求，不主动运行未修改模块或全仓测试。
2. 不能运行时必须记录原因和替代验证。
3. Bug fix 必须优先添加或说明无法添加回归测试。
4. 共享包改动必须至少运行相关 unit tests 和受影响 app 的 type/build。
5. 每个新增或修改接口调用的小模块必须有对应 `*.test.ts` 或 `*.test.tsx`，允许一个模块测试覆盖多个调用文件，但必须维护可追溯的调用文件和接口函数清单；逐个接口至少验证已等待响应、成功后继续和失败时阻断 callback、下一步、关闭、刷新、成功提示或成功态消费。不得只依赖统一 request/helper 的单一测试替代调用点测试。

## 完成后

1. 在 `.ai/runs/<date>-<task-name>/` 生成本地 run log。整个目录已加入 `.gitignore`，运行记录只在本机查看，不提交或通过 `git add -f` 强制加入版本控制。
2. 汇总修改文件、测试结果、风险、未解决事项。
3. 判断是否更新 `.ai/context`、`.ai/prompts`、`.ai/agents`、`.ai/skills`、`.ai/mcp`、`.ai/checklists`、`.ai/decisions`。
4. 不要声称未验证内容已经通过。

## 长期规则筛选

只有稳定、可复用、会影响后续开发的发现才写入长期规则。一次性问题写入 run log 或 `KNOWN_RISKS.md`。
